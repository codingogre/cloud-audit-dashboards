Cloud Audit Suite Review

How well the seven dashboards and eleven Discover sessions serve SOC analysts, compliance auditors, platform admins and security managers: where the design gets in their way, which of their questions it answers, and what comes next.

Reviewed 2026-10-26 against release 1.0.7, updated for 1.0.7.1Use cases Design holes Project Audit Test (serverless 9.6)
Summary

Investigation works; evidence and reporting lag

  • Most questions are partly answered. Of customer use cases, are answered outright and partly. The usual gap is the last step: a count no panel adds up, an export that loses its context, or a field the stream has but no panel shows.
  • Following an identity works. The Identity type and Identity dropdowns reach every kind of credential, API keys included, and every identity table and treemap tile clicks through to Identity 360 with the identity pinned. What's left: a session-bar zoom has no way back, the raw-event links don't carry the page's filters, and there is no picker for one index or one saved object.
  • Six alert rules watch the sharpest signals; behaviour alerts come later. The starter pack raises failed-sign-in bursts, a sign-in after failed sign-ins, new API keys and role changes, security changes at an unusual hour, new identities, and audit events that stop arriving. The rules ship disabled with no delivery of their own, so each customer turns them on and routes them. use cases still need a rule or longer retention: alerts against an identity's own baseline (1.2.0), checks that need months of history, and first access to a Kibana space (UC-112).
  • Evidence and reporting are the weakest area. Row caps are stated only in titles, exports drop the query and the time range, and there is no one-page summary or scheduled report.
  • Managers are served least. Headline tiles compare with the previous period, but there is no posture summary to share.

Alerting gaps

Questions that need a rule, not a dashboard

Six rules ship with the suite on Kibana's Universal Alerting: Failed sign-in burst, Successful sign-in after failed sign-ins, New API key or role change, Security change at an unusual hour, New identity seen, and Audit events stopped arriving. They answer UC-002, UC-003, UC-032, UC-049, UC-050 and UC-125, cover part of UC-129, and alert on each new identity for UC-070. Below are the rules still to build. Each sketch names the Kibana rule type, the condition in ES|QL using the suite's ECS field names, and a schedule. They're starting points to tune, not finished rules.

Compared with elastic-audit-logs-awesome · 2026-10-25

Ideas from another audit project

elastic-audit-logs-awesome works with a different log: the Elasticsearch and Kibana audit logs of Elastic Cloud Hosted and ECK deployments, which the operator configures and ships themselves. This suite reads the Elastic Cloud serverless audit stream. So the comparison is of ideas, not data: for each of its 57 capabilities, whether this suite has the same idea, plans it, or could use it. New gaps

  • Their validation suite documents what the log does not show. In their log, an ES|QL query on an index the caller may not read was recorded as access_granted, while _search on the same index recorded the denial; requests rejected before authorization were never logged; and a forged or revoked key carried no key id. The serverless stream may or may not behave the same. The idea is to test cases like these with synthetic scenarios and write down the blind spots found. Medium · a test and docs, any release
  • No timeline of security changes. Every change is in the Config changes tables, but nothing plots them over time: change type down the side, time across, coloured by who made it. Low · not yet in a release
  • Synthetic personas share one address. Their test traffic runs from a separate machine per persona group, so their location panels show several places. Ours all comes from one IP. Low · test harness only

Ideas they reinforce

  • Alert rules shipped as code, as their settings-change rule is. The suite ships six, deployed with the dashboards.
  • An alert when audit events stop arriving. Their docs warn that a quiet alert proves nothing if logging stopped. Use case UC-125 asks for it, and the suite's rule Audit events stopped arriving answers it.
  • Risk tiles on Identity 360 for destructive Elasticsearch actions (index, data stream and snapshot deletes, delete-by-query), which this suite's risk model does not weigh today.
  • Roles on Identity 360 (a design hole above) and changes made to an identity by someone else, both on the roadmap, and an off-hours count, which the rule Security change at an unusual hour covers for security changes.
  • One index's or one saved object's whole history behind a picker. Their Dataset 360 and Kibana Object 360 pages do this; here it is a design hole above, and an Index family dropdown on Elasticsearch Data Access would cover the index half.

The 14 specific to their setup configure the audit log itself: which events are written, filters that drop routine traffic at the source, and how logs are shipped. Serverless customers do not configure the audit stream. The nearest idea here is the noise gate, which hides routine traffic when the dashboards query it instead of dropping it at the source.

Roadmap

From here to full coverage

Every open design hole and every use case not answered today, placed in the release that closes it. Patch releases add to the dashboards, and 1.0.7 continues as a run of small ones, 1.0.7.2 to 1.0.7.7; 1.1.0 adds a dashboard; 2.0.0 brings in data from outside the audit stream. Expand a release for its use cases and holes.

    How the alert pack works: the rules run on Kibana's Universal Alerting, ship disabled, and carry no delivery of their own; each customer routes them with an action policy on the tag cloud-audit. Thresholds start from the sketches in this review. There are no fixed business hours: the unusual-hour rule judges each identity against its own last 30 days, in UTC, so it works for any time zone. "New identity seen" compares with the last 30 days.
